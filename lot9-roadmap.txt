1. Comment utiliser ce document
Ce document est votre carnet de route. Il liste, dans l'ordre, tous les lots à réaliser après le Lot 1.
Chaque lot est un petit ensemble cohérent, livré dans un fichier zip, que vous testez avant de passer
au suivant. On n'avance jamais au lot suivant sans votre validation.
Pour chaque lot, vous trouvez :
 •  l'objectif et les prérequis ;
 •  la liste numérotée des étapes (cases à cocher) ;
 •  les règles métier à respecter ;
 •  les livrables attendus ;
 •  les critères de validation : ce que vous devez vérifier avant d'accepter le lot ;
 •  les décisions que vous devez prendre, avec les valeurs que je propose par défaut.
 
Les trois statuts :
 LIVRÉ
Livré, testé et remis dans un zip.
 EN COURS
Commencé, mais pas encore livré. Les parties déjà faites sont indiquées.
 À FAIRE
Pas encore commencé.
Important. Les lots 2 à 17 sont une planification. Les contenus pourront être ajustés selon vos
décisions et ce que nous découvrirons en testant. Chaque ajustement sera noté ici dans le journal
d'avancement (annexe B).

LOT 2
Socle applicatif et authentification
 EN COURS
Phase 1 (Foundation), partie A · Sprint 1
Objectif. Obtenir une application Next.js qui démarre, se connecte à la base avec le rôle restreint
mojo_app, authentifie les utilisateurs de façon sûre, parle FR/Kreyòl/EN et s'installe comme PWA.
Prérequis
 •  Lot 1 installé : base migrée (001 à 009) et Super Administrator créé.
 •  Node.js 20 ou plus sur la machine de développement.
 
Déjà fait
 ✓  Migration 010 (fonction log_event pour l'audit applicatif, fonction latest_usd_htg pour le dernier
 taux).
✓  Projet Next.js + TypeScript initialisé : package.json, tsconfig, next.config avec en-têtes de
 sécurité, .env.example, dépendances installées.
✓  Reste à écrire et tester : tout le code listé ci-dessous (non encore livré).
 
Étapes à réaliser (dans l'ordre)
 ☐  2.1  Couche base de données : pool PostgreSQL et fonction withUser qui ouvre une transaction et
 pose app.user_id et app.ip, afin que l'audit et la RLS identifient l'utilisateur.
☐  2.2  Connexion : vérification bcrypt, message d'erreur identique que le compte existe ou non,
 verrouillage temporaire après N échecs (paramètre app_settings), journalisation de chaque
tentative.
☐  2.3  Sessions : jeton aléatoire, seul son hash SHA-256 est stocké, cookie httpOnly +
 SameSite=Lax (+ Secure en HTTPS), expiration configurable, révocation à la déconnexion.
☐  2.4  Récupération de compte : jeton à usage unique (validité 1 h) généré par un administrateur,
 page de réinitialisation, invalidation des sessions existantes après changement de mot de passe.
☐  2.5  Middleware : redirection vers la connexion sans session ; routes publiques limitées
 (connexion, réinitialisation, santé, manifest, service worker).
☐  2.6  Internationalisation : fichiers fr.json, ht.json, en.json ; langue enregistrée par utilisateur
 (cookie avant connexion) ; dates et montants formatés selon la langue.
☐  2.7  Argent : fonctions de formatage HTG/USD, conversion avec le dernier taux saisi, bascule
 d'affichage HTG/USD par utilisateur ; mention claire si aucun taux n'existe.
☐  2.8  Structure d'écran : sidebar filtrée par permissions, topbar (recherche globale, notifications,
 langue, devise, menu utilisateur), fil d'Ariane, identifiant visuel discret par direction.
☐  2.9  Pages : connexion, réinitialisation, profil (mot de passe, langue, devise), accès refusé, page
 introuvable, pages « bientôt disponible » pour les modules non encore construits.
☐  2.10  PWA : manifest, icônes 192 et 512, service worker minimal avec page hors ligne, installation
 sur téléphone.
☐  2.11  Point de santé /api/health pour la supervision.
 ☐  2.12  Docker : Dockerfile de l'application et service app dans docker-compose ; guide
 d'installation mis à jour.
Règles métier à respecter
 •  Aucun secret dans le code ; tout vient de .env.
 •  L'application se connecte uniquement avec mojo_app, jamais avec le propriétaire de la base.
 •  Le contrôle de permission se fait côté serveur ; l'interface ne fait que masquer.
 
Livrables
 •  mojo-erp-lot2.zip (code, migrations, Docker, README à jour).

Finance : taux, comptes, caisse et transactions
 À FAIRE
Phase 2 (Finance), partie A · Sprint 3
Objectif. Pouvoir enregistrer correctement revenus et dépenses en HTG et en USD, avec des soldes
fiables.
Prérequis
 •  Phase 1 validée (Lots 2 et 3).
 
Étapes à réaliser (dans l'ordre)
 ☐  4.1  Taux de change : saisie manuelle (HTG pour 1 USD) avec date, historique, rappel si aucun
 taux n'est saisi pour la journée.
☐  4.2  Comptes : caisse, banques, mobile money, par entité ; solde d'ouverture ; vue des soldes.
 ☐  4.3  Catégories de revenus et de dépenses : hiérarchie, par entité ; liste initiale à valider avec
 vous.
☐  4.4  Transactions : saisie de revenus, dépenses et ajustements ; le taux est figé au moment de la
 saisie ; numérotation ; pièces justificatives.
☐  4.5  Cycle de vie : brouillon, en approbation, validée, rejetée, contre-passée.
 ☐  4.6  Validation avec séparation des tâches : la personne qui crée ne valide pas sa propre
 opération.
☐  4.7  Contre-passation : correction par écriture inverse liée à l'originale ; aucune suppression
 silencieuse.
☐  4.8  Transferts entre comptes d'une même entité.
 ☐  4.9  Caisse : ouverture, clôture et comptage journalier avec calcul d'écart (nouvelle migration
 011).
☐  4.10  Paiements et encaissements ; dettes et remboursements.
 ☐  4.11  Listes avec filtres, recherche et export ; formulaire mobile « ajout rapide d'une dépense ».
 ☐  4.12  Tests financiers : arrondis, deux devises, immuabilité, validations simultanées, cohérence
 des soldes, données réalistes.
Règles métier à respecter
 •  Montants toujours en décimal exact, jamais en nombre flottant.
 •  Toute transaction porte son entité, sa devise et son taux figé.
 •  Une transaction validée ne se modifie ni ne se supprime.
 
Livrables
 •  mojo-erp-lot4.zip.
 •  Jeu de données de test réaliste.
 •  Rapport de tests financiers.
 
Critères de validation (à vérifier par vous)
 ☐  Une dépense de 500 USD et une de 20 000 HTG donnent le bon total dans les deux devises
 d'affichage.
☐  Tenter de modifier ou supprimer une transaction validée échoue ; la contre-passation fonctionne.
 ☐  Le solde de chaque compte correspond au calcul manuel sur 50 opérations de test.
 
Décisions à prendre
 •  Comptes initiaux (caisse, banques) et soldes d'ouverture.
 •  Liste des catégories.
 •  Règle de numérotation des pièces.

Annexe A. Procédure de reprise : avec qui et
comment continuer
Pour toujours savoir où reprendre, suivez ces étapes au début de chaque nouvelle séance de travail :
 1.  Ouvrez ce document et repérez le dernier lot validé dans le tableau de suivi (section 2).
 2.  Travaillez dans le projet « MoJo ERP » de Claude, afin que les décisions déjà prises restent
 disponibles.
3.  Joignez à la conversation le dernier zip livré et ce PDF.
 4.  Écrivez un message court, par exemple : « Je reprends le projet MoJo ERP. Dernier lot validé : Lot
 2. Continue avec le Lot 3. Voici le zip et la feuille de route. »
5.  Si un test a échoué chez vous, copiez le message d'erreur complet dans la conversation ; ne
 résumez pas.
6.  À la fin du lot, testez avec les critères de validation, cochez la case, notez la date, puis passez au
 suivant.
Où reprendre si quelque chose est bloqué
 •  Installation ou base de données : reprendre au guide du README du dernier zip.
 •  Doute sur une règle métier : les documents du dossier docs/ du Lot 1 font foi (livrables 1 à 10).
 •  Changement de décision : dites-le simplement ; je mettrai à jour le lot concerné et le journal
 d'avancement.
Règles permanentes du projet
 •  Aucun pourcentage du fonds d'urgence, aucun seuil d'approbation, aucun taux de change n'est
 codé en dur : tout est configurable.
•  Une transaction validée ne se modifie ni ne se supprime ; on corrige par contre-passation.
 •  Les permissions sont contrôlées côté serveur et, pour RH et salaires, côté base de données.
 •  Chaque opération sensible est inscrite dans le journal d'audit, qui ne peut pas être modifié.
 •  On avance module par module, avec tests et validation, sans jamais mélanger plusieurs lots.
 •  Les règles de paie, de congés et de fiscalité doivent être validées par un comptable ou un juriste
 avant utilisation réelle.
•  Les traductions kreyòl et anglaises doivent être relues par une personne de confiance.
 •  Les sauvegardes sont testées en restauration avant toute mise en production.
